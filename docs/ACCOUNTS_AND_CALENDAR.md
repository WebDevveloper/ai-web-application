# Профиль, календарь и карта — 20 октября 2026

## Данные и группа

В дампе 688 групп, включая буквенные номера вроде `26А-111`. Занятия связаны с `navigator.dim_groups` через `group_name`; доступны дни недели, интервалы действия и даты сессии. Координат корпусов нет — только адреса.

Аккаунт сохраняет имя, email, хеш пароля и группу. Публичный справочник можно смотреть гостем. Для вошедшего пользователя `/dashboard`, `/schedule`, `/schedule/week` и `/chat` берут группу из профиля на сервере, игнорируя переданный клиентом другой номер. Смена группы выполняется через `PATCH /api/auth/profile` с проверкой справочника. Дедлайны выбираются для этой группы и общие. Недостающие дедлайны не придумываются из расписания.

Миграция `003_accounts.sql` добавляет `users` и `user_sessions`. Профиль ссылается на постоянную `study_groups`, куда выбранный код добавляется при необходимости. Он не зависит от заменяемых строк снимка: повторный импорт не удаляет аккаунты.

## Авторизация

- `bcryptjs`, cost 12, отдельная случайная соль. Соль и cost уже входят в строку хеша. Пароль — от 12 символов и не более 72 байт UTF-8; более длинный ввод отвергается, а не обрезается. Argon2id тоже подходит новому сервису; bcrypt выбран по требованию проекта.
- JWT подписывается HS256 и действует 8 часов. В нём идентификаторы пользователя/сессии, issuer, audience и срок, без email, пароля и группы. Сервер проверяет подпись, алгоритм, срок и запись сессии. Выход удаляет запись, отзывая JWT сразу. Автоматического продления нет.
- Cookie `campus_session`: `HttpOnly`, `Path=/api`, `SameSite=Lax`, в production — `Secure`. Токен не отдаётся в JSON и не хранится в localStorage.
- Изменения аккаунта требуют `X-Campus-Request: 1`; CORS разрешает только заданные источники. Вход/регистрация вместе ограничены 10 попытками за 15 минут на IP. Лимитер хранится в памяти процесса; для нескольких инстансов понадобится общий store.
- История диалогов локальная, с отдельным ключом аккаунта и группы. Это разделение интерфейса, не шифрование браузерного хранилища. Старый общий ключ истории не импортируется в аккаунт автоматически. На общем компьютере удаляйте диалоги и выходите из аккаунта.

Восстановление пароля, подтверждение email, университетский SSO и синхронизация истории не подключены. Выбор группы не подтверждает обучение и не открывает закрытые университетские данные. Для пилота с реальными пользователями отдельно нужны жизненный цикл аккаунта и правила обработки персональных данных.

## Обновление локально

Сделайте резервную копию БД. В рабочей ветке:

```bash
git switch codex/campus-mvp-implementation
git pull --ff-only
npm ci
cd server
npm ci
npm run db:migrate
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Последняя команда генерирует секрет. Запишите его в `server/.env` как `JWT_SECRET`, не отправляйте в Git или чат. При уже загруженном снимке повторный импорт не нужен.

```dotenv
JWT_SECRET=значение_сгенерированное_у_себя
NAVIGATOR_ENABLED=true
COOKIE_SECURE=false
COOKIE_SAME_SITE=lax
CLIENT_ORIGINS=http://localhost:5173
```

`COOKIE_SECURE=false` — только для локального HTTP. В production задайте `NODE_ENV=production` и `COOKIE_SECURE=true`; небезопасная комбинация останавливает запуск. Перезапустите backend/frontend. Используйте одинаковый hostname: `localhost` на обоих адресах либо `127.0.0.1` на обоих, с соответствующим CORS.

Если дамп ещё не подключён, следуйте [NAVIGATOR.md](NAVIGATOR.md). При выключенном навигаторе группы берутся из прежней `study_groups`.

## Netlify и backend на Render/Railway

Предпочтительны запросы `/api` через домен frontend. Тогда браузеру не нужны сторонние cookie между доменами хостингов.

На **Netlify** задайте `API_PROXY_TARGET` равным HTTPS origin backend, например `https://your-service.onrender.com`, без `/api`. Удалите старое непустое `VITE_API_URL`: production-клиент по умолчанию использует относительный `/api`. Сборка создаст `dist/_redirects` с правилом proxy; Netlify обрабатывает его раньше SPA-правила из `netlify.toml`. Пример домена в документе не является вашим сервером.

На **backend**:

```dotenv
NODE_ENV=production
JWT_SECRET=свой_постоянный_случайный_секрет
COOKIE_SECURE=true
COOKIE_SAME_SITE=lax
CLIENT_ORIGINS=https://ваш-сайт.netlify.app
```

`DATABASE_URL` прежняя. Примените миграцию перед запуском новой версии. `TRUST_PROXY_HOPS` задайте по реальной цепочке доверенных proxy; за одним proxy — `1`. Не включайте безусловное доверие всем proxy. С Netlify proxy проверьте, какой IP видит backend: лимит входа не должен становиться общим для всех посетителей. Реальные proxy, cookie и TLS хостинга здесь не проверялись.

При прямых запросах с другого домена потребуется `COOKIE_SAME_SITE=none` и `COOKIE_SECURE=true`, но браузер может блокировать сторонние cookie. Предпочтительнее proxy или frontend/backend на одном сайте.

После размещения проверьте регистрацию, перезагрузку страницы, выход и повторный вход на production-домене. Не меняйте JWT_SECRET с каждым деплоем — это завершает все сессии.

## Календарь

`GET /api/schedule/week?groupCode=261-321&startDate=2026-10-19` возвращает семь дней и дедлайны диапазона. UI показывает неделю с понедельника, поддерживает переход по неделям и выбор даты. Даты и сроки отображаются по Москве, независимо от часового пояса устройства.

Backend делает семь ограниченных запросов существующего отбора расписания. При росте нагрузки следующий шаг — единый SQL-запрос диапазона и кэш по группе/неделе/версии снимка; отдельный сервис до измерения нагрузки не добавлен.

Диалог понимает «Расписание на эту неделю», «Расписание на следующую неделю», «Расписание на неделю с 2026-10-19» без вызова ИИ. Произвольные формулировки дат поддерживаются не полностью. Подгруппы не разделяются автоматически. Пустая ячейка не считается подтверждённым выходным.

## Карта и маршруты

Список включает все загруженные корпуса. Поиск аудитории позволяет выбрать её корпус для карты. Пути внутри здания нет: источник не содержит этажных планов и графа проходов.

Без ключа после нажатия загружается виджет с адресом, маршрут открывается в Яндекс Картах по ссылке. С `VITE_YANDEX_MAPS_API_KEY` используется JavaScript API 2.1 с панелью маршрутизации прямо в приложении: ручное отправление, общественный транспорт, пеший и автомобильный маршрут. Живое построение маршрута с ключом проекта ещё нужно проверить.

Получите ключ «JavaScript API и HTTP Геокодер» в кабинете Яндекса, проверьте условия/лимиты и ограничьте доменами проекта. `VITE_`-ключ виден в браузере — так работает браузерный SDK. Серверные секреты туда помещать нельзя. После изменения нужна новая сборка frontend.

«Маршрут от меня» делает один запрос Geolocation API после нажатия. Нужны HTTPS (локально localhost) и разрешение браузера. Отказ/тайм-аут не блокируют ручной ввод и внешнюю ссылку. Координаты не отправляются нашему backend и не сохраняются в localStorage; для маршрута передаются Яндексу. Это местоположение устройства, не обязательно GPS-датчик.

## Проверки

`npm run check`: ESLint, backend-тесты в PGlite/PostgreSQL 18, компонентные тесты в jsdom и сборка. Для полного дампа задайте `NAVIGATOR_TEST_DUMP_PATH`, как в NAVIGATOR.md. Рабочая БД не используется.

Проверяются cost/соль, длина пароля, cookie, неверные подпись/алгоритм JWT, истечение и отзыв, группа профиля, CSRF, недельные сроки. В компонентах проверяются помощь → диалог, календарь, гостевой выбор группы, разделение истории, карта с имитацией SDK и геопозиции.

Добавлен `npm run test:e2e` с отдельным локальным API на БД в памяти и Vite. Требуется `npx playwright install chromium`. Стенд не использует рабочие JWT_SECRET/DATABASE_URL и не предназначен для production.

В текущей среде Chromium скачался повреждённым, а удалённый браузер не подключился к локальному стенду. Поэтому e2e и визуальная проверка desktop/mobile не завершены. Компонентные тесты не заменяют настоящий браузер.
