# План тестирования и валидации

## Автоматические проверки

На 20 октября 2026 года добавлены аккаунты, сессии, группа профиля, неделя и компонентные тесты интерфейса. Подробности запуска и ограничения браузерной проверки: [ACCOUNTS_AND_CALENDAR.md](ACCOUNTS_AND_CALENDAR.md).

Также проверяются:

- ESLint для frontend и backend;
- production-сборка Vite;
- нормализация запросов и обратной связи;
- классификация пяти типов вопросов;
- выбор даты «завтра» с часовым поясом кампуса;
- разбиение Markdown на фрагменты;
- запрет вызова модели для расписания;
- запрет вызова модели при отсутствии источника;
- ответ по проверенным фрагментам без API-ключа;
- возврат к проверенным фрагментам при ошибке AI-провайдера;
- передача модели найденного контекста и формирование карточек источников.

Команда полного прогона:

```bash
npm run check
```

SQL навигатора и откат импорта проверяются во встроенном PostgreSQL 18 через PGlite. Полный предоставленный дамп отдельно прогнан вместе с тремя миграциями и seed; документы приложения сохранились. Это не проверка сетевого подключения и TLS вашего сервера. Порядок запуска дополнительного теста с внешним дампом описан в [NAVIGATOR.md](NAVIGATOR.md).

Полный прогон 20 октября: 38 backend-тестов с внешним дампом и 11 компонентных тестов прошли, пропусков нет; ESLint и production-сборка завершились успешно. Отдельно проверена сборка Netlify proxy. Браузерный e2e-прогон не выполнен: архив Chromium скачался повреждённым, удалённый браузер не видит локальный стенд. Карта проверена с имитацией SDK; живой маршрут и внешний вид нужно проверить с ключом проекта в настоящем браузере.

## Контрольный набор вопросов

Создайте не менее 30 вопросов на основании интервью и реальных документов. Для каждого вопроса заранее укажите ожидаемый сценарий, допустимый ответ и правильный источник.

| Категория | Минимум вопросов | Пример |
|---|---:|---|
| Расписание | 5 | «Какие пары завтра?» |
| Дедлайны | 5 | «Что сдать до пятницы?» |
| Навигация | 5 | «Как пройти в корпус А?» |
| Обращения | 5 | «Куда писать, если не работает кабинет?» |
| Документы | 8 | «Как получить справку об обучении?» |
| Нет ответа | 2 | вопрос, которого нет в подключённых материалах |

Для поиска измеряется `Recall@5`: доля вопросов, для которых правильный фрагмент попал в первые пять результатов.

## Пользовательский тест

Рекомендуемый минимум для итерации — 5–8 первокурсников из разных учебных групп и 2 сотрудника, которые отвечают на типовые обращения.

Сценарий одной сессии:

1. Попросить участника выполнить пять задач без подсказок ведущего.
2. Записать время, успешность и места затруднений.
3. После каждой задачи спросить, доверяет ли участник ответу и заметил ли источник.
4. В конце провести короткое интервью: что было непонятно, чего не хватило, где участник искал бы информацию без ассистента.
5. Не объяснять интерфейс заранее: иначе тест измеряет качество инструкции, а не продукта.

## Метрики MVP

| Метрика | Как считать | Цель первой проверки |
|---|---|---:|
| Успешность задачи | выполненные задачи / все попытки | не ниже 80% |
| Время до ответа | от формулировки задачи до найденного решения | медиана до 60 секунд |
| `Recall@5` поиска | правильный источник в топ-5 | не ниже 85% |
| Покрытие источниками | справочные ответы с источником / все справочные ответы | 100% |
| Полезность ответа | `helpful` / все оценки | не ниже 70% |
| Критические выдуманные факты | ответы, противоречащие источнику | 0 |
| Понятность следующего шага | оценка 4–5 по шкале 1–5 | не ниже 75% |

Целевые числа являются гипотезами команды, а не уже достигнутыми результатами. После первой серии тестов в пояснительную записку нужно внести фактические значения, размер выборки и перечень изменений.

## Проверка стейкхолдером

Владелец каждого источника должен подтвердить:

- что документ можно использовать в пилоте;
- что он не содержит лишних персональных данных;
- кто и как часто проверяет актуальность;
- какой канал считать официальным при расхождении;
- какие вопросы ассистент обязан передавать человеку без попытки ответа.
